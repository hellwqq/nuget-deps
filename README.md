# depgraph — визуализатор графа зависимостей NuGet

Конфигурационное управление, практическая работа № 2, вариант 24.

## 1. Общее описание

CLI-инструмент на Python 3 (только стандартная библиотека), который по
конфигурационному файлу INI получает зависимости пакета .NET (NuGet),
строит граф зависимостей и визуализирует его.

Статус: **все 5 этапов выполнены**.

## 2. Настройки (`config.ini`, секция `[settings]`)

| Параметр       | Описание                                              |
|----------------|-------------------------------------------------------|
| `package_name` | имя анализируемого пакета                             |
| `repository`   | URL репозитория или путь к файлу тестового репозитория |
| `test_mode`    | режим тестового репозитория (`true` / `false`)        |
| `version`      | версия пакета                                         |
| `output_file`  | имя файла с изображением графа (`*.png`)              |
| `ascii_tree`   | вывод зависимостей в виде ASCII-дерева                |
| `max_depth`    | максимальная глубина анализа (целое, >= 1)            |

Все параметры обязательны. Ошибки (нет файла, нет секции, пустое или
неверное значение) выводятся как `error: ...`, код возврата 1.

## 3. Сборка и тесты

Сборка не нужна. Требуется Python 3.9+ и установленный Graphviz
(утилита `dot` в `PATH`) для получения PNG. Тесты (стандартный
`unittest`; тесты, которым нужен `dot`, пропускаются без Graphviz):

    make test

## 4. Запуск и примеры

    ./run.sh                      # config.ini по умолчанию
    ./run.sh -c my.ini
    ./run.sh --show-config        # дополнительно вывести параметры
    ./run.sh --direct             # только прямые зависимости (этап 2)
    ./run.sh --edges              # граф в виде «пакет -> зависимости»
    ./run.sh --load-order         # порядок загрузки (этап 4)

Пример вывода этапа 1:

    package_name = Newtonsoft.Json
    repository = https://api.nuget.org/v3/index.json
    test_mode = False
    version = 13.0.3
    output_file = graph.png
    ascii_tree = True
    max_depth = 3

### Этап 2: прямые зависимости

Используется формат NuGet V3. Без менеджеров пакетов и сторонних
библиотек: читается service index (`PackageBaseAddress`), затем
скачивается `<id>/<версия>/<id>.nuspec`, из него извлекаются все
элементы `dependency` (зависимости всех target framework объединяются).
Версией зависимости считается нижняя граница диапазона (`[1.0, )` → `1.0`),
как выбирает NuGet (lowest applicable version).

    $ ./run.sh -c config.ini
    <имя зависимости> <версия>

### Этап 3: граф зависимостей

Граф строится рекурсивным BFS (`graph.bfs_level`): функция обрабатывает
один уровень и рекурсивно вызывает себя для следующего.

* `max_depth = N` — пакет, лежащий на глубине N, попадает в граф, но
  не раскрывается (корень имеет глубину 0, `1` = только прямые зависимости).
* Циклы: уже известный пакет повторно в очередь не ставится, ребро к нему
  сохраняется, поэтому обход всегда завершается (в том числе `A: A`).

**Тестовый репозиторий** (`test_mode = true`): `repository` — путь к файлу,
строка `A: B C` значит «A зависит от B и C», имена — заглавные латинские
буквы, `#` — комментарий. Пакет без строки считается листом.

    $ ./run.sh -c examples/cycle.ini
    A -> B
    B -> C
    C -> A D
    D -> D

Примеры: `examples/simple.*`, `examples/cycle.*`, `examples/diamond.*`
(файл `.txt` — репозиторий, `.ini` — конфиг).

### Этап 4: порядок загрузки

`--load-order` печатает порядок, в котором нужно загружать пакеты:
зависимости раньше зависимых, запрошенный пакет — последний
(обход в глубину, пост-порядок, `loadorder.load_order`). Рёбра, замыкающие
цикл, пропускаются, о них выводится предупреждение в stderr.

    $ ./run.sh -c examples/simple.ini --load-order
    1. D
    2. B
    3. E
    4. C
    5. A

**Сравнение с реальным менеджером пакетов (NuGet).** Проверяется командами
(нужен установленный .NET SDK, в проект добавлен нужный пакет):

    dotnet new console -o cmp && cd cmp
    dotnet add package <имя> --version <версия>
    dotnet restore -v detailed      # порядок установки в логе
    dotnet list package --include-transitive

Ожидаемые расхождения и их причины:

* NuGet скачивает и распаковывает пакеты **параллельно**, жёсткого порядка
  загрузки у него нет — в логе порядок может отличаться от запуска к запуску.
  Наш порядок — детерминированный топологический.
* NuGet работает с одним target framework проекта, а инструмент объединяет
  зависимости всех групп `.nuspec` — граф может содержать больше пакетов.
* При нескольких путях к пакету NuGet выбирает версию по правилу
  «nearest wins» и поднимает версию до максимальной нижней границы;
  инструмент берёт версию при первом обнаружении (BFS).
* NuGet не ограничивает глубину и сообщает о циклах ошибкой NU1108,
  инструмент обрывает цикл и выводит предупреждение.

### Этап 5: визуализация

После построения графа (всегда) инструмент:

1. формирует описание на языке Graphviz и сохраняет его в `*.dot` рядом
   с PNG (`visualize.to_dot`);
2. сохраняет изображение в PNG-файл `output_file` (`dot -Tpng`);
3. при `ascii_tree = true` печатает ASCII-дерево: `(cycle)` — ребро
   замыкает цикл, `(*)` — поддерево уже было напечатано выше.

Пример (`./run.sh -c examples/diamond.ini`):

    A
    |-- B
    |   `-- D
    |       `-- E
    |           `-- F
    `-- C
        `-- D (*)
    graph saved: examples/diamond.png, examples/diamond.dot

DOT для `examples/simple.ini`:

    digraph "A" {
        rankdir=LR;
        node [shape=box];
        "A" -> "B";
        "A" -> "C";
        "B" -> "D";
        "C" -> "D";
        "C" -> "E";
        "D";
        "E";
    }

Файлы `*.png` и `*.dot` — результат запуска, в репозиторий не входят
(см. `.gitignore`).

**Три реальных пакета** (нужен доступ к nuget.org):

    ./run.sh -c examples/nuget-logging.ini      # Microsoft.Extensions.Logging 8.0.0
    ./run.sh -c examples/nuget-serilog-file.ini # Serilog.Sinks.File 5.0.0
    ./run.sh -c examples/nuget-polly.ini        # Polly 8.4.0

**Сравнение со штатными средствами NuGet:**

    dotnet add package <имя> --version <версия>
    dotnet list package --include-transitive
    dotnet nuget why <проект> <пакет>

Возможные расхождения: `dotnet list` показывает зависимости только для
target framework проекта, а инструмент объединяет все группы `.nuspec`;
NuGet разрешает конфликты версий («nearest wins»), инструмент берёт
первую найденную нижнюю границу; `max_depth` в NuGet отсутствует.

### Результаты сравнения с dotnet list package

Сравнение выполнено при `max_depth = 10`. Штатный инструмент запускался
в консольном проекте на net11.0 командой
`dotnet list package --include-transitive`.

| Пакет                              | dotnet: транзитивные пакеты                    | depgraph: пакетов в графе (с корнем) |
|------------------------------------|------------------------------------------------|--------------------------------------|
| Polly 8.4.0                        | Polly.Core 8.4.0                               | 83                                   |
| Microsoft.Extensions.Logging 8.0.0 | Microsoft.Extensions.DependencyInjection 8.0.0 | 88                                   |
| Serilog.Sinks.File 5.0.0           | Serilog 2.10.0                                 | 78                                   |

Результаты расходятся. Файл `.nuspec` хранит зависимости в группах по
target framework. NuGet выбирает одну группу, подходящую проекту, а
depgraph объединяет зависимости всех групп, в том числе старых
`netstandard1.x`, откуда приходит большое дерево пакетов `System.*`,
`NETStandard.Library` и `runtime.*`.

Из-за объединения групп в графе появляются циклы, которых нет внутри
одной группы. Пример для Microsoft.Extensions.Logging:
`System.Memory -> System.Numerics.Vectors -> NETStandard.Library ->
System.Net.Http -> System.Diagnostics.DiagnosticSource -> System.Memory`.
Инструмент обрывает такой цикл и помечает его `(cycle)` в ASCII-дереве.
